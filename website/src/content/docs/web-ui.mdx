`herdr web` serves a browser interface to Herdr. It runs as its own process, separate from any session server, so it can list every session and let you pick one.

This is for reaching your own machine over a private network such as WireGuard or an SSH tunnel. It is not a hosted service.

## Why a separate process

Each Herdr session has its own server, and a session server only knows its own session. Only a process outside them can enumerate every session and offer a chooser. `herdr web` is that process: one listener, one port, all sessions.

The gateway proxies the same JSON API the CLI uses. The browser never attaches as a terminal client, so opening the web UI does not affect the layout or size of your terminal panes.

## Enable the gateway

The gateway is disabled unless a key is configured. This is deliberate: an open gateway is remote shell access, so it never listens without authentication.

Put the key in `config.toml` so it survives restarts:

```bash
key=$(head -c 32 /dev/urandom | base64)
```

```toml
[web]
key = "the key you generated"
```

```bash
chmod 600 ~/.config/herdr/config.toml
herdr web
```

Without a key it exits with a diagnostic instead of binding a port.

The key must be at least 16 characters. It is compared in constant time, and it is never written to logs.

Because a key in `config.toml` is only as private as that file, Herdr refuses to start when the file is readable by other users and tells you to run `chmod 600`. Use `HERDR_WEB_KEY` for a one-off run instead.

## Configuration

```toml
[web]
# Address to listen on. Default: 127.0.0.1
bind = "127.0.0.1"
# TCP port. Default: 8787
port = 8787
# Directory containing the built web UI. Optional.
static_dir = "/home/you/herdr/web/dist"
# Optional Origin allowlist. Empty disables the check.
allowed_origins = []
# URL `herdr update web` downloads the page from. Optional.
update_url = "https://github.com/ogulcancelik/herdr/releases/download/web-ui/herdr-web-ui.html"
# Gateway key. Keep this file at chmod 600.
key = "..."
```

Prefer binding a private interface over `0.0.0.0`, so the port is only reachable from the network you intend.

Key sources, in order of precedence:

- `HERDR_WEB_KEY`
- `HERDR_WEB_KEY_FILE`, a file containing the key
- `[web] key` in `config.toml`

A file-based source must not be readable by other users, and Herdr enforces that for `config.toml` and for `HERDR_WEB_KEY_FILE`.

## Serving the UI

The gateway serves the UI from `static_dir` at request time; it is never embedded in the herdr binary, so you can update or replace it independently. When `static_dir` is unset, only the WebSocket endpoint is served.

Build the bundled UI with:

```bash
cd web && bun install && bun run build
```

That produces a single self-contained `web/dist/index.html`. Point `static_dir` at the `dist` directory.

Each release also publishes the same file as the `herdr-web-ui.html` asset, so you can use a released UI without building anything. The UI changes independently of the herdr binary, so there is also a rolling `web-ui` release that always holds the newest build:

```bash
mkdir -p ~/herdr-web
curl -fsSL -o ~/herdr-web/index.html \
  https://github.com/ogulcancelik/herdr/releases/download/web-ui/herdr-web-ui.html
```

Point `static_dir` at that directory. Downloading a versioned release asset works the same way; the asset name is identical.

Because the gateway serves the page itself, the page and the WebSocket share an origin, so no extra hosting or CORS setup is needed.

### Updating the page

Because the page is a file rather than part of the binary, it is updated on its own:

```bash
herdr update web            # download and install the newest page
herdr update web --check    # report what is available, writing nothing
```

This requires `static_dir` (there has to be a directory to write into) and `update_url`:

```toml
[web]
static_dir = "/home/you/herdr-web"
update_url = "https://github.com/ogulcancelik/herdr/releases/download/web-ui/herdr-web-ui.html"
```

The download is written to a temporary file and then renamed over `index.html`, so a failed or interrupted download cannot leave the gateway serving a partial page. A file that does not look like a herdr web UI build — a proxy error page, a truncated transfer — is rejected rather than installed.

Each build carries its version in a comment, which is what `--check` compares:

```html
<!-- herdr-web-ui version: 0.7.21 -->
```

When both the installed page and the downloaded one carry a version, an identical version means there is nothing to do. Reload the page in your browser after updating; the gateway serves the file from disk on each request, so no restart is needed.

`herdr update` with no subcommand updates the binary, not the page. The two are released separately, so neither updates the other.

### Publishing the page

For a change that only touches the UI, publish the page on its own:

```bash
just web-publish
```

That builds `web/` and uploads the result to the rolling `web-ui` release, which is where `update_url` points. No herdr release is created and no platform binaries are rebuilt, because none of them changed.

Because the marker is what decides whether an update installs, a UI-only publish stamps a distinct one by default — `<crate version>+web.<timestamp>` rather than the bare crate version. Without a distinct marker the download would match what is installed and `herdr update web` would report the page as already up to date. Pass a version to choose your own:

```bash
just web-publish 0.7.24
```

`just web-status` reports what is installed and what was built last.

## Connecting

Open the gateway URL in a browser, enter the key, then pick a session or type a new name.

- Opening a session that is not running starts its server.
- Session names use letters, numbers, `.`, `_`, and `-`.
- Several clients can attach to one session and share its state.

When you store the key, the UI also remembers the session you opened and returns to it after a page reload. Leaving a session with the back button clears that memory, so a reload keeps you on the picker.

### Addresses and reloads

The screen you are on is in the URL, so a reload lands where you were rather than back at the key form:

```
#                      pick a session
#/<session>            that session's agents
#/<session>/<pane>     one agent's conversation
```

Opening a conversation adds a history entry, so the browser's Back and Forward buttons move through the app. A link to a conversation can be shared or bookmarked, and opening one directly works as long as the connection is remembered. Without a remembered key there is nothing to reconnect with, so the key form is shown first.

### Losing the connection

A phone browser suspends a backgrounded tab, which drops the WebSocket, so returning to the page would otherwise show a frozen view with no sign that nothing is arriving. The header carries a small state dot: green while connected, pulsing while it is retrying, and a tappable **reconnect** once the automatic attempts have given up. Reconnecting restores the session and its subscriptions, so a backgrounded tab picks up where it left off.

## Screens

The UI is a native page, not a terminal mirror. Nothing here renders ANSI; every screen is built from the JSON API.

**Sessions.** Every session Herdr knows about, with whether it is running, plus a field to open an existing session or start a new one.

**Agents.** The agents in the selected session, grouped by workspace and showing each one's current state. A running agent is tinted green — its name, its status dot, and the border of the panel it is in — so activity is visible while scanning the list instead of only in the small status pill. Tap an agent to open it.

**Agent detail.** One agent, with its recent output, a message composer, and — when the agent is waiting for input — the key bar described below.

## The agent console

Output is plain text taken from the pane, so it uses normal browser scrolling, text selection, and copy on every platform.

While an agent is working, new output appears as it is produced, and the view stays at the newest turn. Scrolling up to read back pauses that, so incoming output does not pull the view away from what you are reading; returning to the bottom resumes it. Scrolling to the top loads earlier output a page at a time, so a long conversation can be read back without loading it all at once. A `start of history` marker shows when there is nothing older to load.

The composer sends a message to the agent. `Enter` sends and `Shift+Enter` inserts a newline.

A sent message appears in the conversation straight away, with an **agent is responding** indicator under it. The agent's own transcript is the real record, so it only contains the message once the agent has written the turn; when it does, the placeholder is replaced by the recorded turn rather than shown twice.

After you send a message, the send button becomes a **stop** button for as long as the agent is working. This is driven by the agent's reported state rather than by which browser sent the message, so opening an agent that is already running also offers the stop control. Stopping sends the same key the agent advertises for interruption (usually `esc`), so it behaves the same as pressing the key yourself.

Local UI state, meaning which screen you are on and how far you have scrolled, is not shared with the terminal. Only the agent's own output and state are.

## Answering a prompt

When the agent is blocked waiting for input, a **waiting for you** panel appears above the composer.

There are two forms of this panel, depending on what the agent tells Herdr.

### Options, when the agent publishes them

Some agents use a structured interaction protocol and can report the question they are waiting on, along with the options they offered. For these, the panel shows the question, each option's label and description, and a **Send answer** button; a choice made here is the choice the agent offered, not a guess about its wording.

Which agents do this:

- **Codex** for command, file, and permission approvals, once its Herdr integration is installed.
- **Claude Code** for tool approvals, the same way.
- **Pi** for questionnaires, when the `@juicesharp/rpiv-ask-user-question` plugin is installed. Only a single-question dialog appears; a multi-question one, and typing a custom answer, stay in the terminal.

A multi-question request is answered in one call, so an agent cannot act on half an answer.

Because the agent's prompt is written to the embedded terminal, the structured panel and the terminal agree; the panel is simply easier to answer, especially on a phone. An agent that offers a structured panel is still fully answerable in the terminal, and the panel is the convenience rather than the only route.

#### The approval window

An approval is answered while the agent is paused before its own prompt, so there is a short window for the reader to answer before the agent gives up and asks in the terminal instead. Codex and Claude Code wait a few seconds by default; if nobody answers in time, the question is withdrawn and the agent shows its normal prompt, so a terminal user is never left waiting on a panel nobody is looking at. Set `HERDR_CODEX_PERMISSION_WAIT_MS` or `HERDR_CLAUDE_PERMISSION_WAIT_MS` in the agent's environment to change that wait.

A Pi questionnaire is different: the dialog is on screen and waiting either way, so Herdr keeps offering it for much longer (`HERDR_PI_ASK_WAIT_MS`, 120 seconds by default). When that ends the panel is withdrawn and the dialog is left exactly as it was.

### Keys, when the agent only reports state

Agents that do not publish a structured request get a panel that shows the last part of the pane as text and offers the keys an agent prompt normally accepts: arrow keys, `Enter`, `Esc`, the number keys, and `y` / `n`.

This panel deliberately does not parse the prompt. It cannot tell which option is which, so it does not try; you read the text and press the key, exactly as you would in the terminal.

This matters for two reasons:

- It cannot select the wrong option, because it never guesses what an option means.
- It keeps working when an agent changes its wording, since nothing is matched against the text.

The keys are sent to the pane as raw terminal input, so they behave the same as typing them into the terminal. `Esc` aborts rather than answers in most agents, so it is styled separately from the keys that resolve the prompt.

## Reading the conversation

Agents that publish their native session file — pi, Claude Code, and Codex, when their Herdr integration is installed — can be shown as a structured conversation instead of a terminal screen: one exchange per turn, with tool calls you can expand and the token count for the session.

The transcript is parsed on the server from the agent's own session log, so it reflects what the agent recorded rather than what its TUI happens to be painting. Deep links into that conversation are available through the pane right-click menu; see [codex-trace links](/docs/configuration/#codex-trace-links).

Each turn shows the answer and any errors, with the agent's thinking and its tool calls collapsed behind a label you can expand. Thinking is usually far longer than the answer, so it stays out of the way until you want it.

A working agent's transcript is polled while it runs. The server does not emit an event when a pane's output grows — only when a pane's title, metadata, or diagnostics change — so a view driven purely by events stops updating the moment the agent starts writing. Polling is what keeps the newest turn appearing as it is produced; it stops when the agent leaves the working state.

### Jumping around a conversation

A narrow rail beside the transcript holds one tick per message you sent, in order. The tick for the turn you are reading is highlighted, so the rail doubles as a position indicator as you scroll.

Hovering a tick shows what that message said, and clicking it scrolls that turn to the top. The ticks stay a compact centred block rather than spreading over the full height, and a session with more messages than fit samples them evenly — the tick you are at is always kept.

On a touch screen the rail floats over the transcript instead of taking a column of its own, so the text keeps the full width, and it fades to a faint hint when it is not being used. Dimmed it ignores touches, so the start of every line stays selectable; touching the transcript or scrolling brings it back to full strength. The labels are not rendered and the ticks grow to a comfortable tap size. There is no hover on a touch device, so a label revealed only by hovering could never appear; tapping the tick jumps instead.

A finger can also press anywhere on the rail and slide up or down to scrub through the messages, previewing each one beside the rail, and jump to wherever it is released. A single tick is a small target on a phone, and a long conversation is sampled so one tick stands for several messages; sliding turns the whole rail into one control instead of asking for a precise tap.

Agents that only report a session id, and plain shells, fall back to the rendered pane.

## Theme

A theme switch sits at the top right of every screen. It toggles between the dark and light palettes, and the choice is remembered in the browser. With no stored choice, the UI follows the operating system's `prefers-color-scheme` setting.

## Mobile use

The layout is built for narrow screens: agent cards stack, the composer stays above the keyboard, and the prompt keys are sized for touch. The page is not a terminal, so there is no viewport sizing to negotiate and no mobile layout mode to trigger — it reflows like any other web page.

Notifications are not delivered to the browser.

## Remote access

WireGuard and SSH tunnels are the intended paths. The transport is plain `ws://` because the tunnel already provides encryption.

Bind to your private address:

```toml
[web]
bind = "10.0.0.5"
```

Or keep the default loopback bind and forward the port over SSH:

```bash
ssh -L 8787:127.0.0.1:8787 you@server
```

The forwarded port is reachable at `ws://127.0.0.1:8787`. Do not expose the gateway directly to the public internet: the key is a single static secret guarding shell access, and it is not a substitute for a tunnel.

If you host the page somewhere other than the gateway, set `allowed_origins` so other sites cannot connect to your gateway from a browser. Note that some browsers also restrict a public HTTPS page from reaching private network addresses.

## Detaching

Leave a session with the back button; the session and its panes keep running. Closing the browser tab detaches cleanly and does not stop the server.

To stop a session and its panes, use `herdr session stop <name>`.

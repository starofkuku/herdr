`herdr web` は Herdr のターミナル UI をブラウザに配信し、ブラウザからの入力をセッションへ橋渡しします。セッションサーバーとは別の独立したプロセスとして動くため、すべてのセッションを列挙して選択させることができます。

これは WireGuard や SSH トンネルなどのプライベートネットワーク経由で自分のマシンに接続するためのものです。ホスト型サービスではありません。

## 独立したプロセスである理由

各 Herdr セッションは独自のサーバーを持ち、セッションサーバーは自分のセッションしか知りません。それらの外側にあるプロセスだけが、すべてのセッションを列挙して選択肢を提示できます。`herdr web` がそのプロセスです。1 つのリスナー、1 つのポート、すべてのセッションを扱います。

ゲートウェイは CLI と同じ JSON API を中継します。ブラウザがターミナルクライアントとして接続することはないため、Web UI を開いてもターミナルペインのレイアウトやサイズには影響しません。

## ゲートウェイを有効にする

キーが設定されていない限り、ゲートウェイは無効です。これは意図的な動作です。開かれたゲートウェイはリモートシェルアクセスそのものなので、認証なしでリッスンすることはありません。

再起動後も有効になるよう、キーは `config.toml` に置きます:

```bash
key=$(head -c 32 /dev/urandom | base64)
```

```toml
[web]
key = "生成したキー"
```

```bash
chmod 600 ~/.config/herdr/config.toml
herdr web
```

キーがない場合は、ポートを bind せずに診断メッセージを出して終了します。

キーは 16 文字以上が必要です。比較は定数時間で行われ、ログに書かれることはありません。

`config.toml` のキーはファイル自体と同じ強度しかないため、Herdr は他のユーザーから読めるファイルでは起動を拒否し、`chmod 600` を案内します。一時的な実行には `HERDR_WEB_KEY` を使ってください。

## 設定

```toml
[web]
# Address to listen on. Default: 127.0.0.1
bind = "127.0.0.1"
# TCP port. Default: 8787
port = 8787
# Directory containing the built web UI. Optional.
static_dir = "/home/you/herdr/web/dist"
# Optional Origin allowlist. Empty disables the check.
allowed_origins = []
# URL `herdr update web` downloads the page from. Optional.
update_url = "https://github.com/ogulcancelik/herdr/releases/download/web-ui/herdr-web-ui.html"
# Gateway key. Keep this file at chmod 600.
key = "..."
```

`0.0.0.0` よりもプライベートインターフェースに bind することを推奨します。意図したネットワークからのみポートに到達できます。

キーの取得元は優先順に次のとおりです:

- `HERDR_WEB_KEY`
- `HERDR_WEB_KEY_FILE`、キーを含むファイル
- `config.toml` の `[web] key`

ファイル経由のキーは他のユーザーから読めてはならず、Herdr は `config.toml` と `HERDR_WEB_KEY_FILE` の両方でそれを強制します。

## UI の配信

ゲートウェイは `static_dir` からリクエスト時に UI を配信します。UI が herdr バイナリに埋め込まれることはないため、独立して更新・差し替えできます。`static_dir` が未設定の場合、WebSocket エンドポイントのみが提供されます。

同梱の UI をビルドします:

```bash
cd web && bun install && bun run build
```

これで単一の自己完結した `web/dist/index.html` が生成されます。`static_dir` をその `dist` ディレクトリに向けてください。

各リリースでは同じファイルが `herdr-web-ui.html` アセットとしても公開されるため、ビルドせずにリリース済みの UI を使えます。

UI は herdr バイナリとは独立して更新されるため、常に最新ビルドを保持する `web-ui` のローリングリリースもあります:

```bash
mkdir -p ~/herdr-web
curl -fsSL -o ~/herdr-web/index.html \
  https://github.com/ogulcancelik/herdr/releases/download/web-ui/herdr-web-ui.html
```

`static_dir` をそのディレクトリに向けてください。バージョン付きリリースのアセットも同じ名前なので、同じ手順で使えます。

ゲートウェイ自身がページを配信するため、ページと WebSocket は同一オリジンになり、追加のホスティングや CORS 設定は不要です。

### ページの更新

ページはバイナリの一部ではなくファイルなので、単独で更新します:

```bash
herdr update web            # 最新のページをダウンロードしてインストール
herdr update web --check    # 何も書き込まず、利用可能な内容だけを報告
```

これには `static_dir`(書き込み先のディレクトリ)と `update_url` が必要です:

```toml
[web]
static_dir = "/home/you/herdr-web"
update_url = "https://github.com/ogulcancelik/herdr/releases/download/web-ui/herdr-web-ui.html"
```

ダウンロードした内容はまず一時ファイルに書き込まれ、その後 `index.html` にリネームされます。したがって、ダウンロードの失敗や中断によってゲートウェイが不完全なページを配信することはありません。herdr web UI のビルドに見えないファイル(プロキシのエラーページ、途中で切れた転送)はインストールせずに拒否します。

各ビルドはコメントにバージョンを含んでおり、`--check` はそれを比較します:

```html
<!-- herdr-web-ui version: 0.7.21 -->
```

インストール済みページとダウンロードしたページの両方にバージョンがある場合、同じバージョンなら何もする必要はありません。更新後はブラウザでページを再読み込みしてください。ゲートウェイはリクエストごとにファイルをディスクから読むため、再起動は不要です。

サブコマンドなしの `herdr update` はバイナリを更新し、ページは更新しません。両者は別々にリリースされるため、互いを更新することはありません。

### ページの公開

変更が UI だけの場合は、ページを単独で公開できます:

```bash
just web-publish
```

`web/` をビルドし、その結果を rolling の `web-ui` リリース(`update_url` が指す場所)にアップロードします。herdr のリリースは作成されず、プラットフォームのバイナリも再ビルドされません。どちらも変更されていないためです。

マーカーが更新をインストールするかどうかを決めるため、UI のみの公開では既定で異なるマーカーを付けます — 素の crate バージョンではなく `<crate バージョン>+web.<タイムスタンプ>` です。マーカーがインストール済みと一致すると、`herdr update web` はページを最新とみなします。任意のバージョンを指定することもできます:

```bash
just web-publish 0.7.24
```

`just web-status` はインストール済みのバージョンと最後にビルドしたバージョンを報告します。

## 接続

ブラウザでゲートウェイの URL を開き、キーを入力してからセッションを選ぶか新しい名前を入力します。

- 起動していないセッションを開くと、そのサーバーが起動します。
- セッション名には英数字、`.`、`_`、`-` を使用できます。
- 複数のクライアントが 1 つのセッションに接続し、状態を共有できます。

キーを保存している場合、UI は最後に開いたセッションを記憶し、ページを再読み込みしてもそこへ戻ります。戻るボタンでセッションを離れるとこの記憶は消えるため、再読み込み後もピッカーにとどまります。

## 画面

UI はターミナルのミラーではなくネイティブなページです。ANSI は一切描画せず、どの画面も JSON API のデータから組み立てられます。

**セッション。** Herdr が把握しているすべてのセッションとその実行状態、および既存セッションを開くか新規に開始するための入力欄。

**エージェント。** 選択中のセッションのエージェントをワークスペースごとにまとめ、それぞれの現在の状態を表示します。タップすると開きます。

**エージェント詳細。** 1 つのエージェントの最近の出力、メッセージ入力欄、そしてエージェントが入力を待っているときに現れるキーバー（後述）。

## エージェントコンソール

出力はペインから取得したプレーンテキストなので、すべてのプラットフォームでブラウザ標準のスクロール、テキスト選択、コピーが使えます。

エージェントが動作している間は、新しい出力が生成されるそばから表示されます。上部までスクロールすると以前の出力を 1 ページずつ読み込むため、長い会話も一度に全部読み込まずに遡れます。これ以上古い内容がない場合は `start of history` マーカーが表示されます。

入力欄はエージェントにメッセージを送ります。`Enter` で送信、`Shift+Enter` で改行します。

メッセージを送信すると、そのターンをエージェントが処理している間だけ送信ボタンが **停止** ボタンに変わります。停止はエージェント自身が中断用に示しているキー（通常は `esc`）を送るため、自分でそのキーを押した場合と同じ動作になります。

ローカルの UI 状態、つまりどの画面にいてどこまでスクロールしたかは、ターミナルとは共有されません。共有されるのはエージェント自身の出力と状態だけです。

## プロンプトへの回答

エージェントが入力を待ってブロックされているとき、入力欄の上に **waiting for you** パネルが現れます。ペインの末尾をテキストで表示し、エージェントのプロンプトが通常受け付けるキー（方向キー、`Enter`、`Esc`、数字キー、`y` / `n`）を並べます。

このパネルは意図的にプロンプトを解析しません。どの選択肢がどれかを判別できないため、判別しようとしません。テキストを読んでキーを押す、というターミナルと同じ操作になります。

これには 2 つの理由があります。

- 選択肢の意味を推測しないため、誤った選択肢を選ぶことがありません。
- テキストに対して何も照合しないため、エージェントが文言を変えても動作し続けます。

キーは生のターミナル入力としてペインに送られるため、ターミナルで入力した場合と同じ動作になります。多くのエージェントでは `Esc` は回答ではなく中止なので、回答に使うキーとは別の見た目にしています。

## 会話を読む

ネイティブのセッションファイルを公開しているエージェント（Herdr インテグレーションを導入した pi、Claude Code、Codex）は、ターミナル画面ではなく構造化された会話として表示できます。1 ターンにつき 1 つのやり取りで、ツール呼び出しは展開でき、セッションのトークン数も表示されます。

トランスクリプトはエージェント自身のセッションログからサーバー側で解析されるため、TUI がたまたま描画している内容ではなく、エージェントが記録した内容を反映します。その会話へのディープリンクはペインの右クリックメニューからコピーできます。詳しくは [codex-trace リンク](/docs/configuration/#codex-trace-links)を参照してください。

各ターンは回答とエラーを表示し、エージェントの思考とツール呼び出しは展開できるラベルの下に折りたたまれます。思考は通常回答よりはるかに長いため、既定では場所を取りません。

動作中のエージェントのトランスクリプトはポーリングされます。ペインの出力が増えてもサーバーはイベントを送信しません(タイトル、メタデータ、診断が変化したときだけです)ので、イベントだけに頼るビューはエージェントが書き始めた瞬間に更新を止めます。ポーリングによって最新のターンが生成されるそばから表示され、エージェントが動作状態を離れると停止します。

セッション ID だけを報告するエージェントと通常のシェルは、描画されたペインの表示にフォールバックします。

### 会話内を移動する

トランスクリプトの横に細いレールがあり、送信したメッセージごとに 1 つのティックを順番に表示します。読んでいるターンのティックがハイライトされるため、スクロール中は位置インジケーターとしても機能します。

ティックにホバーするとそのメッセージの内容が表示され、クリックするとそのターンが先頭までスクロールします。ティックは高さ全体に広がらず、コンパクトな中央のブロックにまとまります。収まりきらない数のメッセージがある場合は均等に間引かれ、現在いるティックは必ず残ります。

タッチスクリーンではラベルを描画せず、ティックはタップしやすい大きさに広がります。タッチデバイスにはホバーがないため、ホバーでのみ表示されるラベルは決して現れません。代わりにティックをタップするとジャンプします。

指でレールの任意の位置を押したまま上下にスライドするとメッセージをスクラブでき、レールの横にその内容がプレビューされ、離した位置にジャンプします。スマートフォンでは 1 つのティックは小さなターゲットで、長い会話では間引かれて 1 つのティックが複数のメッセージを表すこともあるため、スライドによってレール全体を 1 つのコントロールとして扱えます。


## テーマ

各画面の右上にテーマ切り替えがあります。ダークとライトのパレットを切り替え、選択はブラウザに記憶されます。記憶がない場合は OS の `prefers-color-scheme` に従います。

## モバイルでの利用

レイアウトは狭い画面向けに作られています。エージェントカードは縦に積まれ、入力欄はキーボードの上にとどまり、プロンプト用のキーはタッチしやすい大きさです。ページはターミナルではないため、ビューポートサイズの調整もモバイルレイアウトモードの切り替えも不要で、通常の Web ページと同じようにリフローします。

通知はブラウザには配信されません。

## リモートアクセス

WireGuard と SSH トンネルが想定された経路です。トンネル自体が暗号化を提供するため、トランスポートは平文の `ws://` です。

プライベートアドレスに bind します:

```toml
[web]
bind = "10.0.0.5"
```

または既定のループバック bind のまま、SSH でポートを転送します:

```bash
ssh -L 8787:127.0.0.1:8787 you@server
```

転送されたポートは `ws://127.0.0.1:8787` で到達できます。ゲートウェイを公共のインターネットに直接公開しないでください。キーはシェルアクセスを守る単一の静的な秘密であり、トンネルの代わりにはなりません。

ゲートウェイ以外の場所でページをホストする場合は、`allowed_origins` を設定して、他のサイトがブラウザからゲートウェイに接続できないようにしてください。一部のブラウザは、公開 HTTPS ページからプライベートネットワークアドレスへの到達も制限することに注意してください。

## デタッチ

戻るボタンでセッションを離れます。セッションとそのペインは動き続けます。ブラウザのタブを閉じるとクリーンにデタッチし、サーバーは停止しません。

セッションとそのペインを停止するには `herdr session stop <name>` を使います。
